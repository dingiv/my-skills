# 调试时期（Debug）

> **调试的本质：建立期望 → 观察现实 → 找到偏差 → 修正。** 不是乱猜，是系统化缩小假设空间。

**进入条件**：代码已经能跑但行为不对；或代码跑不起来；或性能不达预期。

**离开条件**：所有已知问题修复完毕 + 回归测试通过 + 行为符合接口契约。

## 一句话

> **调试 = 三阶段循环（重现 → 定位 → 修复）+ 验证；任何阶段都可以回到上一阶段。**

## 何时使用

- 程序崩溃 / panic / 抛出异常
- 程序能跑但输出不对
- 性能不达预期
- 间歇性 bug（有时对有时错）
- 第三方依赖行为不符合预期
- 测试用例失败

## 调试三阶段

### 阶段 1：重现（Reproduce）

**目标**：把 bug 稳定触发出来——只有能重现的 bug 才能修。

| 步骤 | 动作 |
| --- | --- |
| 1.1 | **最小化用例**——剥掉无关输入，只保留触发 bug 的最小集合 |
| 1.2 | **记录环境**——OS、语言版本、依赖版本、配置、内存/CPU 状态 |
| 1.3 | **稳定触发**——重复运行 10 次，确认触发率 |
| 1.4 | **记录预期 vs 实际**——明确写出"应该是什么"和"实际是什么" |

**判断标准**：

- ✅ 能用一段命令 / 一个测试用例稳定触发
- ❌ 触发条件不明，无法重现 → 不能进入阶段 2，先回到 1.1 缩小用例

### 阶段 2：定位（Localize）

**目标**：找到 bug 的精确位置（哪个文件 / 哪一行 / 哪个状态）。

| 方法 | 适用场景 |
| --- | --- |
| **二分法** | 知道大致范围，缩到一半一半试 |
| **加日志 / print** | 不知道状态在哪步变了 |
| **读堆栈** | 程序崩了 |
| **断点调试** | 知道大概在哪函数 |
| **静态阅读** | 代码逻辑明显有误 |
| **diff / bisect** | 上次还好这次坏了 |

**定位的判据**：

- ✅ 能说"在这行 / 这个状态 / 这个输入下，期望是 X、实际是 Y"
- ❌ 只能说"感觉不对" → 没定位完，继续挖

### 阶段 3：修复（Fix）

**目标**：改对 bug。

| 原则 | 说明 |
| --- | --- |
| **最小改动** | 只改必要的，不顺手"优化" |
| **先写失败测试** | 修复前先有能复现的测试 |
| **修复后看测试通过** | 不能让别的测试挂 |
| **回归测试** | 跑全套相关测试 |

**验证**：

- [ ] bug 触发场景不再触发
- [ ] 新写的测试通过
- [ ] 已有测试不挂
- [ ] 修复可解释（不是"试试看居然好了"）

## 跨语言通用方法

### 加日志（最常用）

- **不要删旧日志**——先加新日志，看到证据再删
- **日志要有上下文**：时间、模块、相关 ID、输入摘要
- **分级别**：DEBUG / INFO / WARN / ERROR 不是装饰，是过滤手段

### 二分法（最省时）

- 知道大致范围时，把范围对半切，验证一半
- 不需要范围时，从输入开始二分

### 读堆栈

- 崩溃 / panic / 异常时第一件事
- 看最顶层调用 + 中间业务层 + 底层原因
- 异步栈：用语言自带的异步栈跟踪

### 调试器（最强大但不一定最快）

- 适合：循环里的状态变化、条件分支、回调链
- 不适合：性能问题、高并发问题、生产环境
- 启动成本高，但定位快

### diff / bisect（找回归）

- "上次还好这次坏了"——用 `git bisect` 二分历史
- 找出引入 bug 的 commit

## 何时用哪种工具

| 场景 | 推荐工具 |
| --- | --- |
| 编译错 | 编译器信息（rustc / tsc）+ 静态分析（clippy / eslint） |
| 运行时崩 | 堆栈 + panic message + 核心 dump |
| 状态错 | 日志 + 断点 + 单步 |
| 性能问题 | profiler（flamegraph / chrome devtools）+ 基准测试 |
| 并发问题 | 日志 + 调试器 + 缩小并发度 |
| 内存泄漏 | heap profiler + valgrind / heaptrack |
| 类型问题 | 类型检查器（tsc --noEmit）+ 编辑器提示 |
| 测试失败 | 测试框架输出 + 缩小测试用例 |

## 常见反模式

| 反模式 | 表现 | 纠正 |
| --- | --- | --- |
| **乱猜乱改** | 不重现就改代码 | 先重现；最小用例 + 稳定触发 |
| **删日志求安静** | 失败信息太烦，删掉 | 失败信息是定位证据 |
| **绕过去** | "调个顺序好像就好了" | 找根因，不要绕 |
| **同时改 N 处** | 一改就 commit 一堆 | 每次只改一处，验证后再改下一处 |
| **不复现就修** | "用户说挂了" | 复现是修复的前提 |
| **修完不验证** | 改完 commit 不跑测试 | 必须跑全套相关测试 |
| **没找根因** | 注释掉出错行 | 这是回避，不是修复 |

## 跟其他阶段的关系

- **来自 [开发早期](early-dev.md)**：开发完一个功能后立刻自测，跑不通进入调试
- **回到 [开发早期](early-dev.md)**：bug 根因是设计错误时，回到设计阶段
- **进入长期维护节奏**：bug 修复模式稳定后，进入维护节奏（流程 / 规范支撑见 [engineering.md](../engineering.md)）

## 一句话

> **调试 = 系统化缩小假设空间；三阶段循环（重现 → 定位 → 修复）+ 验证；先重现后修复，先测试后提交。**
