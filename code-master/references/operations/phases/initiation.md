# 立项时期（Initiation）

> **立项 = 把模糊需求逼成清晰接口契约与调用链。** 这个阶段不下任何代码，所有产出都是文档和伪代码——但它们决定后续开发的所有方向。

**进入条件**：用户首次提出"做一个 X 系统 / 设计一个 X / 搭一个 Y"。这是整个项目生命周期的第一步。

**离开条件**：产出 `REQUIREMENTS.md` + 对外接口契约 + N 条端到端 calltree，用户全部确认。

## 一句话

> **4 步流程：需求阐述 → 需求文档 → 接口契约 → 调用链罗列。** 每步完成必须向用户确认才能进入下一步。

## 何时使用

- 用户提出"做一个新项目"
- 用户提出"从零设计一个 X"
- 用户提出"帮我搭一个 Y 系统"
- 任何**没有现存代码、需求模糊**的新建项目请求

## 核心流程（4 步）

### 第 1 步：需求阐述（跟用户对话）

**目标**：把模糊的"想做一个项目"逼成清晰的需求边界。这一步只产生对话，不产出文件。

**核心问题骨架**（必须问到这几类，缺一不可）：

1. **项目目的** —— 要解决什么问题？为什么做？替代什么 / 补足什么空缺？
2. **目标用户** —— 谁会用？典型使用场景是什么？
3. **核心场景** —— 最关键的 1–3 个场景是什么？每个场景的「触发 + 输入 + 终止」是什么？
4. **完成标准** —— 做到什么程度算「做完了」？有没有可验证的判定标准？
5. **约束条件** —— 技术栈、性能、部署、时间、团队规模、必须用 / 不能用的东西？

**自由追问**（agent 应根据回答自行判断，决定问什么 / 问几个）：

- 用户的回答哪里不清晰 → 追问
- 用户的回答前后矛盾 → 标注冲突让用户澄清
- 用户跳过了关键问题 → 礼貌地补问
- 用户已经覆盖了所有骨架 → 不必硬凑问题

**第 1 步结束标准**：

- 上述 5 类问题都得到了至少粗略的回答
- agent 能向用户复述「所以你的项目是 X，主要做 Y，服务 Z，对吗？」
- 用户确认无误

**不要做**：

- 不要替用户回答（「你是不是想要 X？」——这会把需求引导向 agent 的预设）
- 不要直接跳到设计（「我猜你想要的是 Y，对吗」——这是把设计阶段的事提前做）
- 不要一次问超过 5 个核心问题（用户会疲劳）
- 不要在这一步写任何代码 / 文档 / 文件

### 第 2 步：生成需求文档

**输入**：第 1 步的对话结论。

**输出**：结构化需求文档 `REQUIREMENTS.md`。

**模板**：

```markdown
# [项目名] 需求文档

## 项目目的
[1–2 段，从第 1 步整理]

## 目标用户
- [用户类型 1]：[典型场景]
- [用户类型 2]：[典型场景]

## 核心场景
### 场景 1：[名字]
- 触发：
- 输入：
- 输出：
- 终止：

### 场景 2：[名字]
[同上]

## 完成标准
- [ ] 标准 1（可验证）
- [ ] 标准 2（可验证）

## 约束条件
- 技术栈：
- 性能：
- 部署：
- 时间：
- 其他：

## 范围外（明确不做的事）
- [从对话中识别，标注哪些是用户明确说不做的]
```

**第 2 步结束标准**：

- 文档已写入文件
- agent 把文档内容向用户复述
- 用户确认无误（特别是「范围外」一节）

### 第 3 步：设计对外接口契约

**输入**：需求文档，特别是「核心场景」与「约束条件」两节。

**输出**：对外接口伪代码，可放 `docs/interfaces/`。

**操作**：

1. 对每个核心场景，先定义 1 个（或一组）对外接口——这些接口是用户/上游能调到的契约
2. 每个接口用**伪代码**定义（不实现），写出输入 / 输出 / 失败语义 / 生命周期
3. 接口由「需求」驱动，不是反过来（不是先想实现，再抽接口）
4. **接口的具体写法参见 [interface-contract.md](../interface-contract.md)**——按程序类型（CLI / Daemon / GUI）选对应形式

**模板**：

```typescript
// [接口名 + 一句话用途]
interface SomeInterface {
  // 输入
  doX(input: InputType): OutputType

  // 失败语义
  //   - InvalidInput → InvalidInputError
  //   - IO 失败 → IOError

  // 生命周期
  init(): void                  // 副作用（连接 / 订阅）在此启动
  destroy(): void               // 关闭后不可再调用
}
```

**罗列要点**：

| 维度 | 检查项 |
| --- | --- |
| **每个场景** | 至少 1 个对外接口 |
| **每个接口** | 输入 / 输出 / 失败语义 / 生命周期齐全 |
| **接口之间** | 不引用未定义的东西 |
| **不写** | 实现细节 / 数据结构 / 拆分模块 / 单元测试 |

**第 3 步结束标准**：

- 每个核心场景的关键接口都有定义
- 接口伪代码自洽（不引用未定义的东西）
- 用户对接口「外观」满意（外观 = 调用方看接口的方式）

### 第 4 步：罗列端到端调用链

**输入**：第 3 步的接口契约。

**输出**：N 条端到端 calltree（每个接口 = 1 条实现链路），可放 `docs/calltrees/`。

**操作**：

1. 从每个对外接口出发，每个接口 = 1 条调用链的实现路径
2. **触发点 → 终止条件**必须明确
3. 主要步骤用 calltree 语法表达，分支细节用 `...` 留白
4. 不画超过 N 条链路（N = 接口数）

**模板**：

```calltree
触发点()                              // 这个接口被调用时进入
    step1()
    step2()
    if 条件:
        分支A()
    else:
        分支B()
    ...                              // 细节留白
    终止()                            // 接口返回 / 通知外部
```

**罗列要点**：

| 维度 | 检查项 |
| --- | --- |
| **入口** | 触发点 = 接口被调用 |
| **主链路** | 主要步骤按因果顺序展开 |
| **分支** | 关键分支标出，细节留白 |
| **终止** | 终止条件明确（成功 / 失败 / 超时）= 接口返回 / 通知 |
| **不画** | 异常处理细节 / 重试逻辑 / 监控点 |

**第 4 步结束标准**：

- 每个接口都有对应的 calltree
- calltree 的触发点 / 终止条件 / 主要步骤可读
- 用户对 calltree 整体走向没有异议（细节留白可接受）

## 流程结束

完成第 4 步后，立项时期结束。产出物清单：

- ✅ `REQUIREMENTS.md`
- ✅ 对外接口契约伪代码
- ✅ N 条端到端 calltree

**后续可以**：

- 进入 [早期开发](early-dev.md)——搭基础设施（logger / config / constants / utils）
- 然后进入 `rust-style` / `ts-style` 开始编码
- 转入迭代开发（边实现边回头修订架构）

## 常见偏离与纠正

| 偏离 | 表现 | 纠正 |
| --- | --- | --- |
| **跳过第 1 步** | 用户给出简短描述后，agent 立刻开始设计接口 | 礼貌地回到第 1 步：「我想先跟你确认几个关键问题，确保后面不偏」 |
| **第 1 步问太细** | agent 把用户问到烦，问题清单 20+ 条 | 收敛到骨架 5 类；非核心问题放到后续迭代 |
| **第 2 步替用户决定范围外** | agent 自己填了「不做 X」但用户没说 | 明确标注「待确认」让用户决定 |
| **第 3 步变成完整实现** | 接口伪代码变成了完整函数 | 立即停手，回到伪代码级别 |
| **第 4 步变成完整设计** | calltree 画得太细，陷入实现细节 | 用 `...` 留白；只在用户追问时展开 |
| **跳过用户确认** | 一步完成直接进下一步 | 每步必须向用户确认无误才能往下走 |
