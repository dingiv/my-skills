# 三种应用模式

code-master 的方法论可应用于三种典型场景。每种场景的入口、判断、操作、产出都不同——**误用就会得到错误的产物**（把模式一用在模式二上 = 无视现状硬切；把模式三当模式二用 = review 越权动手）。

## 模式一：架构新项目（0 → 1）

**触发**：从零开始一个项目，没有现存代码。

**核心判断**：

- 需求是否清晰到能拆成端到端链路？
- 团队是否理解"先定架构再写代码"的价值？
- 时间预算是否允许先做架构文档？

**操作**：直接走工作流四子步（见 [workflow.md](workflow.md)）。

1. 需求 → 拆链路
2.1 入口 → 定义空间
2.2 接口 → 伪代码契约
2.3 依赖 → 单向无环
2.4 空间 → 单一职责拆分

**产出**：

- 架构文档（含端到端链路图）
- 模块 / 接口的伪代码契约
- 单向依赖图
- **可立刻进入编码阶段**的骨架（接口 + 工厂函数 + 销毁函数）

**典型陷阱**：

- 跳过架构直接开始写代码——前两周很快，第四周开始崩。
- "完美架构"病——过度设计、把方法论用成教条。
- 需求没拆清就定接口——接口会反复改。

## 模式二：架构重构（已有项目 → 目标架构）

**触发**：项目能跑，但架构出了问题——耦合过紧、依赖环、改一处崩三处、单元测试写不下去、新人 onboarding 痛苦。

**核心判断**：

- 是真要重构，还是先小修小补就够？
- 业务是否允许阶段性重构（按链路分批迁移）？
- 团队是否有精力维持双轨（老代码 + 新骨架共存）？

**关键差异**：**起点不是空白，是已有代码**——必须先理解现状，再设计目标，最后分阶段迁移。这与模式一的"先定目标再实现"**方向相反**。

**操作**（四步，方向与模式一相反）：

1. **画现状** —— 用 `calltree` 画出已有的端到端链路。不是为了好看，是为了让"我们到底在维护什么"达成共识。
2. **找痛点** —— 把每条链路对照自查清单（见 [self-check.md](self-check.md)）+ 反模式表（见 [anti-patterns.md](anti-patterns.md)），列出真问题。区分"架构病"与"实现 bug"——后者不在重构范围内。
3. **定目标** —— 按工作流四子步，为每条重做的链路定义目标架构。**只重构有问题的链路**，不要顺手改没问题的。
4. **分阶段迁移** —— 制订迁移计划：
   - 优先重构"被依赖最多的模块"——收益最大、风险也最大，先做。
   - 每阶段必须保留可运行状态——双轨共存，老代码桥接到新骨架，逐步切换。
   - 每阶段完成后删除老代码——不留下"双份实现"。

**产出**：

- 现状 calltree（理解"我们有什么"）
- 问题清单 + 优先级（决定"先动哪里"）
- 目标架构文档（与模式一相同）
- **分阶段迁移计划**（模式一没有）

**典型陷阱**：

- "大爆炸重写"——试图一次写完整个新版本，几乎必然失败。
- 不画现状直接动手——团队对"现在长啥样"没有共识，重构完了发现新代码和旧代码做的事不一样。
- 重构与功能改进并行——分不清"重构了什么"和"加了新逻辑"，回归测试难以定位。
- 重构完不删旧代码——双份实现 = 维护噩梦。

## 模式三：架构审视（in-progress 项目）

**触发**：项目进行中，需要评估当前架构质量、判断是否需要干预。

**核心判断**：

- 是在做架构 review（评估质量），还是在做架构重构（动手改）？本模式只做前者。
- 是否有可执行的干预时间窗？review 没时间改 = 浪费。
- 是否能接触到核心维护者？看不到 commit 历史的 review 是盲的。

**关键差异**：**不动代码，只出判断**——产出是评估报告 + 行动项清单，不是代码改动。

**操作**（四步）：

1. **标链路** —— 列出当前已实现 + 计划中的端到端链路。已实现的用 calltree 画出来；计划中的标"待确认"。
2. **过自查清单** —— 逐条对照 [self-check.md](self-check.md) 的自查清单，标红 / 黄 / 绿。**红 = 必须改，黄 = 应该改，绿 = 保持**。
3. **扫反模式** —— 对照 [anti-patterns.md](anti-patterns.md) 的反模式表，识别已存在的架构病。每条反模式标"严重度 × 频度"——决定优先级。
4. **出行动项** —— 输出可执行的行动项清单：
   - **紧急**：阻断业务、引发线上问题的（如循环依赖导致无法热更新）。
   - **重要**：技术上必须改的（如入口不唯一导致难以测试）。
   - **可选**：长期改善但可推迟的（如某些模块的命名不一致）。

**产出**：

- 现状 calltree（与模式二的第一步相同）
- 自查清单评分（红 / 黄 / 绿）
- 反模式扫描结果（按严重度 × 频度排序）
- **行动项清单**（紧急 / 重要 / 可选）

**典型陷阱**：

- "全红"报告——指出所有问题但不区分优先级，等于没说。
- review 不接触代码——只看文档做评审，等于隔靴搔痒。
- 把架构审视当作重构授权——review 只评估、不动手；要动手必须进入模式二。
- 与性能 review 混在一起——架构 review 看的是结构性合理性，不是运行时表现。

## 三种模式的对照

| 维度 | 模式一：架构新项目 | 模式二：架构重构 | 模式三：架构审视 |
| --- | --- | --- | --- |
| 起点 | 空白 | 已有代码 | 已有代码（不改动） |
| 方向 | 需求 → 架构 → 代码 | 现状 → 目标 → 迁移 | 现状 → 评估 → 行动项 |
| 核心动作 | 工作流四子步 | 工作流四子步 + 迁移计划 | 自查 + 反模式扫描 |
| 产出 | 架构文档 + 骨架代码 | 现状 + 目标 + 迁移计划 | 评估报告 + 行动项清单 |
| 是否动代码 | 是（写新代码） | 是（改老代码） | 否 |
| 时间预算 | 较短（设计先行） | 较长（双轨 + 迁移） | 最短（评估即可） |

> **选择哪个模式，不要拍脑袋**——拍脑袋选错了，所有后续动作都会偏移。判断的快捷问句：「今天我要做的是创造、改造还是评价？」
