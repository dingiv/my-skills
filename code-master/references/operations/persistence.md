# 持久化状态管理（Persistence State Management）

> **持久化 = 数据建模 → 选格式 → 选持久化模式 → 加载 → 保存 → 同步 → 崩溃恢复。** 文件型持久化（不覆盖真正的数据库），覆盖客户端 + 服务端通用纪律。

## 一句话

> **建模（A）+ 格式（B）+ 模式（C）+ 加载（D）+ 保存时机（E）+ 内存磁盘同步（F）+ 原子性与崩溃恢复（G）——七件事按这个顺序走完，文件型持久化就立得起来。**

## 何时使用

- 项目初始化——决定持久化策略（schema / 格式 / 模式 / 加载方式 / 保存策略 / 同步模型）
- 引入新数据实体——走 A 数据建模
- 写加载 / 保存 / 同步逻辑——参考 D / E / F
- 崩了之后 / Code review——查 F / G 的反模式

## 跟 file-management.md §5 的关系

`file-management.md` §5 已经讲了持久化模块的**归属纪律**——单一 owner / 4 节点 / 只加载一次 / 显式持久化 / 内存副本是派生缓存。本章**不重复**这一层，只讲归属之外的工程化角度：A 建模、B 格式、C 持久化模式、D 加载、E 保存、F 同步、G 崩溃恢复。两份一起读才完整。

## A. 数据建模（起点）

### A.1 模型定义

业务实体的代码化表达，由三件事组成：

- **类型**——字段名 + 类型（基本 / 枚举 / 嵌套 / 集合 / 可选）
- **校验**——长度 / 范围 / 格式 / 必填 / 默认值
- **序列化**——怎么写到文件、怎么读回来

三件事**必须在同一处声明**——改模型只改一处，所有读写路径自动同步。Rust 用 serde derive + validator；TS 用 zod / typia；其他语言各自有 schema-as-code 工具。

### A.2 标识（主键）

| 策略 | 特点 | 适用 |
| --- | --- | --- |
| **UUID / ULID** | 全局唯一、可分布式生成、占空间 | 多端写入 / 跨进程 |
| **自增 ID** | 顺序、轻量、紧凑、易读 | 单进程单源 |
| **复合 key**（业务字段组合） | 业务天然唯一、可读 | 业务字段本身唯一 |

### A.3 关系建模

两种方式，差别在「数据是合在一起还是分开」：

- **内嵌（聚合根）**：关联实体作为字段嵌套，整个一起读、一起写
- **引用（关联）**：只存对方 ID / key，按需查询 / 拼接

**选内嵌**的判据：关联紧密 / 强一致要求 / 数据小 / 一起访问频率高
**选引用**的判据：关联松散 / 单条实体很大 / 跨集合查询 / 各自生命周期独立

### A.4 模型 / DTO / API 视图三层分离

持久化系统里至少有三套结构，各司其职：

| 层 | 关注 | 谁拥有 |
| --- | --- | --- |
| **模型（Model）** | 文件里长什么样 | 持久化模块 |
| **业务对象（Domain）** | 内部处理逻辑 | 业务模块 |
| **DTO（API view）** | 对外契约 | 接口层 |

**三层合一** = 改格式 = 改所有调用方。**三层分离** = 持久化格式变更只动持久化模块，业务对象 / DTO 各自保持稳定。

### A.5 Schema-as-code

模型定义 = 类型 + 校验 + 序列化约定，三者在**同一份代码**里。改一处全程序同步。

反模式：模型在 DB schema、类型定义在代码、校验规则在前端——三处分散，任何一处改了另两处忘了 = bug。

## B. 存储格式

### B.1 格式选型

| 类别 | 代表 | 体积 | 性能 | 人类可读 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 文本类 | JSON / YAML / TOML | 大 | 慢 | ✅ | 配置 / 小数据 / 人要编辑 |
| 二进制 | MessagePack / bincode / protobuf | 小 | 快 | ❌ | 状态 / 大数据 / 高频读 |
| 嵌入式 DB | SQLite / sled | — | 中 | ❌ | 复杂查询 / 自带索引 |

选择判据：数据量、读写频率、是否需要人手编辑、是否跨语言。

### B.2 自描述 vs 外置 schema

- **自描述**（JSON/TOML/MessagePack）：字段名随数据走——灵活、加字段容易
- **外置 schema**（二进制 / protobuf）：schema 跟数据分离——紧凑、强 schema 强制

**演进能力**：自描述容易加字段；外置 schema 需要明确的 schema 演进规则。

### B.3 格式头：magic + version

文件开头固定字节（magic）+ 版本号，让读端识别格式、决定走哪个 reader。

```
[4-8 字节 magic][1-2 字节主版本][1-2 字节次版本][数据...]
```

- **没格式头** = 升级格式 = 旧数据加载崩溃
- 旧版 reader 读到新格式 → 显式拒绝 + 提示升级（不要尝试猜测）
- 新版 reader 读到旧格式 → 决定是兼容读、迁移还是拒绝

### B.4 物理布局

| 布局 | 优点 | 缺点 |
| --- | --- | --- |
| 整个状态一个文件 | 简单，原子写容易 | 任意改动 = 全写 |
| 一种实体一个文件 | 粒度细、按需加载 | 跨实体引用需拼接 |
| 索引 + 数据文件 | 查询快 | 复杂度高（接近 DB） |

选型：状态总量 / 实体间引用密度 / 单次查询粒度。

## C. 持久化模式

### C.1 全量快照（snapshot）

每次写整个文件。最简单；任何时刻磁盘上 = 完整状态。

- 缺点：数据大时写慢、IO 多
- 适合：小数据 / 状态变化频繁但总量小

### C.2 追加日志（append-only log）

每次只追加一条变更事件。启动时 replay 日志重建状态。

- 优点：写快、有审计
- 缺点：日志增长 → 需要周期性 compaction（重写成 snapshot）
- 适合：变更频、状态可从事件派生、需要审计

### C.3 WAL（write-ahead log）

先写日志到磁盘 → 再改内存。崩了从日志恢复。DB 的做法。

- 优点：高频写仍强一致
- 代价：实现复杂度高、磁盘 IO 多

### C.4 混合：snapshot + log

定期写 snapshot + snapshot 之后的 log。启动时 load snapshot + replay 之后的 log。

实战常用——平衡恢复速度与日志增长。

### C.5 选型

| 模式 | 写成本 | 启动成本 | 适用 |
| --- | --- | --- | --- |
| 全量快照 | 高（每次写全） | 低（一次 load） | 数据小、变化频 |
| 追加日志 | 低（追加一条） | 高（replay） | 需要审计、变化频 |
| WAL | 低 + 强一致 | 中 | 高频写 |
| Snapshot + log | 中 | 中 | 大多数通用场景 |

## D. 加载策略

### D.1 启动全量加载（eager）

进程启动时一次把磁盘数据全部加载到内存。

- 适合：数据小、启动后大量查询
- 简单：所有读走内存、写完同步到磁盘

### D.2 按需懒加载（lazy）

启动时只加载索引 / 元数据；实体按需从磁盘读。

- 适合：数据中等、单次访问粒度小
- 索引放内存可查询 → 按需加载具体实体

### D.3 流式 / 不全载入

从磁盘流式读取、不在内存保留完整集合。

- 适合：数据很大、顺序处理
- 此时通常已经是 DB 边界——考虑真 DB

### D.4 选型

- 数据能放内存 + 大量查询 → eager
- 数据中等 + 单条访问 → lazy + 内存索引
- 数据超过内存 → 不在文件型范围了，DB 接手

## E. 保存策略（时机与频率）

### E.1 触发时机

| 触发 | 频率 | 崩了丢多少 | 适用 |
| --- | --- | --- | --- |
| 每次变更立即写（write-through） | 每次 | 0 | 关键状态、数据小 |
| 显式 `persist()` 调用 | caller 触发 | caller 决定 | 调用方明确知道何时持久化 |
| 周期性 flush | 周期 | 最近一次 flush 之后 | 高频写、性能敏感 |
| 关闭时 flush | shutdown 时 | 所有未保存 | 崩了可重建 |
| 混合：debounce + 周期 + 关闭 | 去抖 + 周期 + 兜底 | 去抖窗口内 | 大多数通用场景 |

### E.2 选型标准

数据丢失容忍度（**业务决定**，不是技术决定）：

- 0 容忍 → write-through
- 分钟级容忍 → debounce + 周期
- 小时级容忍 → 周期 flush
- 崩了可重建 → 关闭 flush 即可

### E.3 不变量

- **graceful shutdown 路径必须 flush**——所有策略的兜底
- **kill -9 不保证 flush**——靠 §G 崩溃恢复兜底

## F. 内存 ↔ 磁盘同步

### F.1 双源问题

持久化系统的两端：

- **内存态**：易失、快、可任意改
- **磁盘态**：持久、慢、需保护

**两边只能有一个是权威源**——混乱的根源就是「两边都改、各自以为权威」。

**默认推荐**：**磁盘是权威源、内存是缓存视图**——崩了只丢缓存视图，从磁盘重新加载即可。

### F.2 同步策略（4 种）

| 策略 | 时机 | 写盘频率 | 崩了丢多少 | 适用 |
| --- | --- | --- | --- | --- |
| **Write-through（直写）** | 内存变更 → 立即写盘 | 每次变更 | 0 | 关键状态、数据小 |
| **Write-back（回写）** | 内存变更累积，定期 flush | 周期 | 最近一次 flush 之后 | 高频写、性能敏感 |
| **Write-behind（异步）** | 先写日志，内存改后台落盘 | 异步 | 同 write-back | 类 DB 场景 |
| **Periodic + on-change（混合）** | change 时去抖，周期 fsync | debounce + 周期 | 去抖窗口内 | 大多数通用场景 |

### F.3 一致性模型

- **强一致**：内存 = 磁盘，任何时刻读磁盘看到最新值——性能差
- **最终一致**：内存超前磁盘 N 秒；flush 后追平——崩了丢 N 秒
- **单调读**：进程内读永远看到单调递增的版本号 / 时间戳

选哪种 = 业务可容忍的丢失窗口 = E 节的输入。

### F.4 进程崩溃在同步中途

「写盘一半崩了」是常态，**必须假设**。

关键不变量：**磁盘上要么是完整旧版本，要么是完整新版本，绝不能是半截。**

解决：见 §G（temp + rename + 校验）。

### F.5 多线程同步

同一进程多线程：内存天然共享，靠锁圈住整个持久化模块。

- **RwLock / 读共享写独占**——读锁可并发、写锁独占
- **避免读写锁外释放**——任何 IO 操作都得在锁内完成（否则读出脏数据）
- 模块内部统一封装，外部只看到「调接口」——锁的细节不外泄

### F.6 多进程同步

内存不共享，必须通过磁盘 / IPC 同步——这一步是文件型持久化的**复杂度上限**。

| 机制 | 用途 |
| --- | --- |
| **文件锁**（flock / fcntl） | 同一时刻只一个进程写 |
| **通知文件 / 监听 fs change**（inotify / FSEvents） | 其他进程感知变更 |
| **共享内存 + 锁** | 高频同步（极少用，复杂） |

**现实**：大多数文件型持久化是单进程——多进程场景就上真 DB，文件型只承担「缓存 / 配置 / 单进程状态」。

### F.7 与加载 / 关闭的关系

持久化有三阶段：

```
加载（启动）：磁盘 → 内存        ←  D 节
同步（运行中）：内存 ↔ 磁盘       ←  F 节（本章重点）
关闭（shutdown）：内存 → 磁盘     ←  E 节兜底
```

三阶段完整覆盖——不要只写加载忘了关闭、只写 set 忘了 persist。

### F.8 反模式

| 反模式 | 后果 | 纠正 |
| --- | --- | --- |
| 内存是权威源（从不写盘） | 崩了丢光 | 明确磁盘是权威源 |
| 磁盘是权威但同步随意 | 两边不一致 | 选 F.2 一种策略并贯彻 |
| 多个持久化模块各写各的 | 写覆盖、数据丢失 | 单一 owner（见 file-management §5） |
| set 完忘 persist | 静默丢失 | write-through 或所有 set 路径配对 persist |
| 多进程无锁写同一文件 | 互相覆盖、文件损坏 | 文件锁，或上 DB |
| 改了内存立即给用户看，没 fsync | 崩了 UI 上有但磁盘没有 | 写入 UI 前必须确认落盘 |

## G. 原子性与崩溃恢复

### G.1 temp 文件 + rename

每次写：

```
1. 写到 <file>.tmp
2. 完整后 rename(<file>.tmp) → <file>
```

rename 在同一文件系统下是**原子的**——任何时刻 `<file>` 是完整旧版本或完整新版本。

**必做**：每次写都走这个流程（无论大小，无论快慢）。

### G.2 fsync

`fsync` 把 OS 缓存刷到盘。

- 没 fsync：写完只是进了 OS 缓存，崩了可能丢
- 何时必须 fsync：所有需要「崩了不丢」的写入
- 性能：fsync 慢——所以 F.2 的 write-back 才有意义（批量合并 + 一次性 fsync）

### G.3 校验

启动时校验文件完整性：

- 长度字段匹配
- magic 头匹配
- 校验和（hash）匹配（如 CRC32 / SHA256）

校验失败 = 文件损坏 / 没写完。

### G.4 backup + 回滚

启动校验失败 → 退回上一份 backup。backup 来源：

- 定期 snapshot（独立文件）——天然 backup
- 手动备份
- 仅配置文件可 git tracked

**不要只存一份**——「单一真相」**不**包括「没有任何备份」。

### G.5 反模式

| 反模式 | 后果 | 纠正 |
| --- | --- | --- |
| 直接覆盖写（不用 temp） | 崩在写一半 → 文件半截 → 数据损坏 | temp + rename |
| 不 fsync | 崩了丢最近写入 | 关键路径必 fsync |
| 没校验和 | 文件损坏后启动 crash 在奇怪的地方 | 启动时校验 + backup 回滚 |
| 唯一一份数据 | 任何损坏 → 数据全丢 | 定期 backup（snapshot 是天然的 backup） |

## 反模式（综合）

| 反模式 | 表现 | 纠正 |
| --- | --- | --- |
| 模型 / DTO / 持久化结构混用 | 改格式 = 改所有调用方 | 三层分离 |
| 模型分散在 DB / 代码 / 前端 | 一改三漏 | Schema-as-code |
| 没格式头（magic + version） | 升级格式 = 旧数据崩溃 | 强制格式头 |
| 业务代码绕过持久化模块直接 IO | 多份副本不一致 | 单一 IO 边界（file-management §4） |
| 内存是权威源 / 磁盘是权威但同步随意 | 双源不一致 | 选 F.2 一种策略 |
| 多持久化模块各写 | 互相覆盖 | 单一 owner（file-management §5） |
| 直接覆盖写不用 temp | 写一半崩 = 文件损坏 | temp + rename |
| 不 fsync | 崩了丢最近写入 | 关键路径必 fsync |
| 没校验和 + 没 backup | 任何损坏 = 数据全丢 | 校验 + 定期 backup |
| 自己实现 DB（数据量超过内存 + 多进程写 + 复杂查询） | 入坑 | 升级到真 DB |

- [ ] 保存策略匹配业务丢失容忍度？

### F. 内存 ↔ 磁盘同步

- [ ] 明确谁是权威源（默认推荐磁盘）？

- [ ] 一致性模型（强一致 / 最终一致 / 单调读）已明示？

### G. 原子性与崩溃恢复

- [ ] 所有写入走 temp + rename？
- [ ] 关键路径有 fsync？
- [ ] 启动有校验（magic + 长度 + 校验和）？
- [ ] 有 backup 机制？校验失败能回滚？

任何一项不满足，去查 [典型反模式](anti-patterns.md) 或对应语言 style。
