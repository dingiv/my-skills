# 工作流：架构设计四子步

需求阐述完成后，架构设计按四个子步推进：接口（即入口）→ 链路 → 依赖 → 空间。四个子步不是串行的瀑布，而是带**反向验证**的迭代：每完成一步，回看前一步是否仍成立；不成立时回到上一步修订，而不是硬往下走。

## 第 1 步：需求阐述 → 定义端到端入口

需求不是「产品功能列表」，而是**触发点 → 终止条件**的一段路径。一段独立的需求 = 一条端到端链路。

操作动作：

- 列出需求 → 拆分成若干条**端到端链路**（「启动流程」「处理一次请求」「配置热更新」「优雅关闭」）。
- 每条链路标注：触发点（不一定是 `main()`）、输入、输出、终止条件。
- 一份好的需求文档，应当能直接画成 calltree（见 `calltree` skill 的「端到端调用链路」原则）。

> **反模式**：把需求写成「系统应当提供 X 功能」「系统应当支持 Y 操作」。这种描述没有触发点、没有终止条件，没法落地——只能变成永远做不完的 backlog。

## 第 2 步：架构设计

四件子事，按因果顺序串起来：

### 2.1 端到端入口设计 → 驱动框架搭建 → 定义空间

入口 = 链路的触发点。这一步做的是「**把空间画出来**」——让每一类资源、每一个状态，都有明确的位置。

具体手段（按项目类型）：

- **单程序 + 事件循环**：CLI、桌面应用、单体服务。`main` 启动 + 事件循环驱动（MVC + 事件循环是典型结构）。
- **多进程 + ZMQ / gRPC**：服务化架构。入口 = 接收端；进程是边界，状态归各自的进程管。
- **库**：入口 = 公开的 API（工厂函数 + 销毁函数）。调用方持有接口，实现不可见。

不论形态，入口的共同要求：

- **入口唯一**：一条链路只有一个触发点（即使内部多入口，外部触发点也要收敛）。
- **入口即边界**：边界内是一台完整的状态机，边界外是另一台状态机。
- **入口即配置**：入口处拿到全部依赖（配置、连接、缓存），向下注入——而不是让各模块各自读全局。

### 2.2 对外接口设计 → 驱动调用链生成

接口是状态机的对外**封装**——调用方通过接口看到的是「能做什么」，而不是「怎么实现的」。**接口先于链路**：先定接口，再为每个接口设计实现链路。

操作动作：

- 对每个核心场景，先定义 1 个（或一组）对外接口——这些接口是用户/上游能调到的契约
- 接口用**伪代码**定义（不实现），写出输入 / 输出 / 失败语义 / 生命周期契约
- 接口设计完成后，**为每个接口设计实现链路**——链路的入口 = 接口被调用，链路的终止 = 接口返回
- 接口的设计应当由**需求**驱动——不是反过来

> **接口的定义顺序：接口 → 链路 → 实现。** 不是：想到一个类型 → 抽接口 → 拼链路；也不是：先画链路 → 再从链路里抠出接口。前者由实现驱动 → 必然过设计；后者把实现当了出发点 → 必然接口散落。**正确路径：先定接口契约（设计 API），再画实现链路（设计 handler 编排）。**

### 2.3 依赖寻找 → 驱动时序定义

这一步回答的是「**什么先、什么后**」。每条链路都隐含一个时序图；架构要做的是把这个时序图**编码进空间布局**。

操作动作：

- 从入口出发，**顺藤摸瓜**：每遇到一个新依赖，问「它的状态从哪来、它什么时候被初始化、它的生命周期覆盖到链路哪里」。
- 把「依赖方 → 被依赖方」画成单向箭头。**不允许反向**（反向 = 循环依赖）。
- 依赖的方向 = 因果的方向：被依赖方**先**就绪，依赖方**后**使用，时序单向。

> **单向依赖是系统性的硬约束**——不是风格选择。一旦允许反向，整套架构的时序都会变成「无法推断」，所有调试、单元测试、并发安全都要重新做。

### 2.4 空间复杂度优化 → 在生命周期约束下尽力拆分

到这一步，骨架已立。最后一步是**让骨架变轻**：

- 按**单一职责**原则拆：一个模块只做一类事，一类事只在一个地方做。
- 拆分时**优先问生命周期**：能否独立成 `init` / `destroy`？能独立才能拆；不能独立的就是耦合，强行拆只会换来「互相看到对方的私有状态」。
- 拆分的目的不是「拆得更细」，是「**降低耦合度**」——拆完以后，每个模块的依赖图应当是浅的、可独立理解的。

> **反模式**：把拆分等同于「拆成更多文件」。文件多 ≠ 模块少；真正的拆分看依赖图：深度和广度都降了，才叫拆完。
