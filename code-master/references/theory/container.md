# 容器（Container）

> **容器是作用域的运行时形态——专门管理某类资源的有限系统，带有明确的治理边界。** HashMap、ApplicationContext、docker 进程，本质都是容器。

## 一句话

> **容器 = 一条治理边界；边界内由容器规则治理（资源隔离 / 依赖管理 / 通信 / 生命周期），边界外只看到统一稳定的接口。**

## 为什么单独讲容器

- [scope.md](scope.md) 讲的是「如何切分空间」（静态概念）
- 本章讲的是「切分后的空间如何治理」（运行时实例）

**典型容器**：

| 容器 | 边界内治理 | 边界外看到 |
| --- | --- | --- |
| `HashMap<K, V>` | 数据如何存储、哈希、扩容 | `get` / `put` |
| `ApplicationContext`（Spring / DI） | 对象构造、依赖装配、生命周期 | 「给我一个实例」 |
| docker 进程 | 文件系统、网络、资源隔离 | 一个可运行的进程 |
| 操作系统进程 | 内存、文件、信号 | 一个可调度的执行单元 |

四者毫无关联，但抽象到「治理边界」层完全同构。

## 四方面治理

容器管理资源，治理边界包括四个相互关联的方面：

1. **资源隔离**——决定装载何种资源，提供何种层次的隔离能力
2. **依赖管理**——为容器内部的资源提供运行环境和依赖
3. **容器间通信**——多实例系统中容器之间的通信和交互
4. **生命周期**——资源有生命周期，容器本身也就具有了生命周期

贯穿这四点的根本约束是**有限性**：容器管理的资源是有限的。正因为有限，才需要边界；试图把无限的东西塞进一个容器，治理就会失效，边界就会泄露。

## 封装从无状态到有状态

普通函数 / API 封装的是一段行为（输入 → 输出映射），**无内部状态**。**容器往前推了一步：封装的是状态 + 行为 + 生命周期的组合体。**

| 封装形态 | 封装的范围 | 控制颗粒度 |
| --- | --- | --- |
| 函数 / API | 行为 | 细 |
| 模块 | 行为 + 部分状态 | 中 |
| **容器** | **行为 + 状态 + 生命周期** | **粗** |

封装得越彻底，控制颗粒度越粗——这是容器的根本代价。

## 空间换时间的容器范式

容器把「用一次性的前置投入换后续重复收益」这条权衡推到了最重的形态：

- `HashMap`：付出桶数组、哈希函数、冲突处理和扩容的空间与写入成本，换回近乎 O(1) 的存取
- `ApplicationContext`：启动时扫描、注册、构建依赖图并做拓扑排序，换回运行时 O(1) 拿到对象
- docker：构建镜像、装系统装依赖，换回环境一致性和可移植性

**判据是同一个变量**——后续使用频率。使用频率不够，前置投入就是纯负担。

## 容器的代价

容器作为最重的封装，**最先付出的是控制颗粒度变粗**：

- `HashMap` 只暴露 `get` / `put` → 无法精确控制 rehash 时机、数据落在哪个桶
- `ApplicationContext` 只返回构造好的对象 → 无法干预装配过程的中间状态
- docker 只给你一个运行起来的进程 → 启动序列、健康检查节奏只剩粗调旋钮

**所有容器都被迫开逃逸舱口**：

- 数据结构容器：迭代时被并发修改抛异常 / 暴露内部数组
- DI 容器：注入不进来时用 `getBean` 手动去捞
- docker：隔离失效时用 `docker exec` 钻进去改

舱口的存在说明：封装越彻底、颗粒度越粗，需要把控制权重新捞回来的场景就越多。**享受了统一的治理边界，代价就是在治理规则覆盖不到、需要细粒度干预时，必须手动穿透容器去操作内部**——这是终极封装必然携带的税，没有哪种容器能例外。

## 容器与系统划分

把「治理边界」放大到整个系统：

- **C4 模型**：系统 → 容器 → 组件 → 代码；容器对应承上启下的那一层（向上对接系统的上下文，向下拆成更细的组件和代码）
- **DDD 限界上下文**：把同样的思想用在业务建模上——同一概念在不同业务域定义不同，必须用边界隔离差异
- **依赖注入的演进**：从内存对象 → 服务发现（跨进程）→ 微服务（跨主机）；注入的形态从内存里的实例变成了网络上的服务端点

**架构设计最难的部分往往不是写代码，而是划定这条边界**。

> **容器 = 用空间边界的封闭性换时间流程的可治理性；封装越彻底，颗粒度越粗，逃逸舱口越必要。**
