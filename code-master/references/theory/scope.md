# 作用域（Scope）

> **复杂需求不能一口气做完——必须拆。** 拆的依据是**作用域**：把状态机的全局作用域切成若干子作用域，把状态放进合适的作用域，以此把状态空间复杂度压回线性。

## 一句话

> **作用域就是空间。** 程序、文件、类、函数都是作用域，每个域有自己的生命周期（**init / set / get / drop** 4 个节点）和状态。**域中状态的所有者就是域本身**——状态管理不依赖外部机制，生命周期跟着域走。

## 为什么需要作用域

- **端到端需求** = 用户直接给出的程序级需求（见 [anatomy.md](anatomy.md)）
- **复杂需求** = 多条端到端链路 + 多种状态 + 多个相互依赖的子系统
- 在一个全局作用域里管理所有状态 = 状态空间爆炸 = 时序错位 + 维护噩梦

**作用域的核心作用**：

1. **空间隔离**——每个作用域有自己的状态集合，外部不能直接访问。
2. **生命周期独立**——每个作用域的展开 / 闭合与其他作用域正交。
3. **接口稳定**——作用域对外只暴露固定接口，内部状态变化不影响外部。
4. **降低状态空间复杂度**——把 N 个全局状态的问题切成 K 个子问题，每个子问题只关心自己作用域内的状态。

## 父子作用域

作用域之间有三种关系：

| 关系 | 含义 | 例子 |
| --- | --- | --- |
| **父子** | 父作用域嵌套子作用域；父依赖子 | 函数调用、模块嵌套、类成员 |
| **兄弟** | 同一父作用域下的多个子作用域；不直接依赖 | 一个模块里的多个子模块 |
| **全局 - 局部** | 全局作用域 = 所有局部作用域的父代 | main 入口 |

**核心约束**：

- **父依赖子**——父作用域要能工作，子作用域必须先就绪（这是 [timing.md](timing.md) 第 1 条「依赖前向包含」的具体形态）
- **兄弟通信走父**——兄弟作用域之间不能直接通信，必须经过共享的父作用域（避免循环依赖）
- **禁止循环依赖**——A 依赖 B、B 依赖 A = 划分错误。纠正：把冲突内容拆到一个新的独立作用域里

## 作用域层级

不同语言提供不同的作用域抽象，从大到小：

```
模块作用域（package / crate / namespace）
  └─ 类作用域（class / struct）
      └─ 函数作用域（function / method）
          └─ 块作用域（block / closure）
```

每一层都可以独立走完 4 个生命周期节点（init / get / set / drop），这是 [workflow.md 第 2.4 步](../operations/workflow.md)「能独立生命周期才能拆」的判据。

## 全局 vs 局部

| 维度 | 全局作用域 | 局部作用域 |
| --- | --- | --- |
| 实例数 | 一次程序运行**只能展开一次** | 可以**展开多次**（每次都是新实例） |
| 生命周期 | 程序启动 → 结束 | 函数调用 → 返回 |
| 适合存放 | 不可变常量、纯函数、单例基础设施 | 局部状态、临时变量、可变状态 |
| 反模式 | 大量可变全局状态 | 把可变状态塞进全局 |

**全局作用域的边界**：

- 可以放：日志、配置、单例进程级资源
- **不能**放：需要反复创建 / 销毁的可变状态——这些必须放进局部作用域
- 必须放时，参考 [ts-style 规则 8「受控的全局状态」](https://example.com/ts-style) 的 4 钩子（init / get / set / destroy）+ 唯一 Owner 模式

## 域的可展开性：单例域 vs 多例域

> **全局级别的域（程序、文件、命名空间）只能被展开一次；类、函数、块可以被展开多次。** 这是域的根本分类维度。

| 类型 | 域 | 展开性 | 含义 |
| --- | --- | --- | --- |
| **单例域**（Singleton Scope） | 程序、文件、全局命名空间 | 一次程序运行只能展开 **1 次** | 状态无法被「销毁重建」——只能原地修改 |
| **多例域**（Multi-instance Scope） | 类、函数、块、闭包 | 一次程序运行可展开 **N 次**（N≥0）| 每次展开都是新实例——可以被销毁重建 |

**这一区分的实质**：

- **单例域**的「状态」= **进程级单例状态**——与进程同生同死
- **多例域**的「状态」= **实例状态**——随每次展开 / 闭合而生灭

## 全局可变状态与函数式编程的根本矛盾

> **函数式编程的不可变更新 = 销毁旧值 + 创建新值。** 但**全局变量无法被重新展开**——这与函数式编程**天生矛盾**。

**推导过程**：

```
FP 的不可变更新模式
  = 局部变量：let x = f(x);  // 销毁旧 x，创建新 x → ✅
  
全局变量的命运
  = 全局 x = new_value;       // 不能销毁（单例域不可重展开）→ 原地修改 → ❌
```

**因此**：

- 在**多例域**（函数、块、类实例）内，FP 的「销毁旧值 + 创建新值」完全可行
- 在**单例域**（全局、文件级 static）内，FP 模式**根本不可行**——只能用「原地修改」
- **「全局可变状态」= 函数式编程的禁区**

**FP 视域下的全局变量「罪状清单」**：

| 罪状 | 后果 |
| --- | --- |
| **不可销毁** | 不可变更新模式（销毁+新建）无法应用 |
| **可重入性丢失** | 同一个变量被多方修改，行为不可预测 |
| **依赖不可见** | 隐式参数（[function-purity.md](function-purity.md) 第 3 子类型）|
| **测试性丢失** | 状态跨测试残留，无法隔离 |
| **并发性丢失** | 多线程读同一变量，要靠锁/同步 |

## 单例域 vs 多例域：实践指南

**单例域**（程序、文件、命名空间）适合放什么：

| 可放 | 原因 |
| --- | --- |
| **常量** | 不可变，没有销毁重建问题 |
| **纯函数** | 无副作用，可任意调用 |
| **单例基础设施** | logger / config loader / DB pool——本来就只该有一份 |
| **4 钩子受控的全局状态** | init / get / set / destroy + 唯一 Owner（见 [ts-style 规则 8](https://example.com/ts-style)）|

| 不可放 | 原因 |
| --- | --- |
| **业务可变状态** | 该销毁重建时无法销毁 |
| **请求级 / 用户级数据** | 不是进程级单例 |
| **跨函数需要「不可变更新」的数据** | 与 FP 模式冲突 |

**多例域**（类、函数、块、闭包）适合放什么：

- 几乎所有**业务逻辑**——每次调用都是新实例
- 需要「不可变更新」的数据结构
- 任何「创建-使用-销毁」生命周期的对象

> **单例域（程序/文件）只能展开一次 → 全局可变状态无法「销毁重建」→ 与函数式编程的不可变更新模式**天生矛盾**。**全局只放常量 / 纯函数 / 受控单例基础设施——其他都进多例域。**

## 域与状态：所有者论断

> **域中的状态是域空间的一部分，域中的状态的所有者就是域本身。**

**三层含义**：

1. **域 = 空间**——域是一个作用域，程序 / 文件 / 类 / 函数都是域，它们都是「空间」
2. **状态属于域**——域中持有的状态，是这个域的「空间的一部分」
3. **域是状态的 owner**——状态的所有者不是「外部某个变量」、不是「全局」、不是「某个 manager」，**就是所在域本身**

**意义**：

- 状态管理不依赖外部机制——owner 就是域，生命周期跟着域走
- 「谁负责 cleanup」这个问题的答案永远明确——**域本身**
- 跨域边界的状态传递 = 所有权转移（move / clone / borrow），不是「泄漏到全局」

## 生命周期的 4 个关键节点

**域有生命周期，状态也有生命周期**。两者必须**绑定**——状态的生命周期 ⊆ 所在域的生命周期。

每个域 / 状态的生命周期有**至少 4 个关键节点**：

| 节点 | 含义 | 常量 | 变量 | IO 资源 |
| --- | --- | --- | --- | --- |
| **init** | 创建 / 初始化 | ✓ | ✓ | ✓（open / connect）|
| **get** | 读取 | ✓ | ✓ | ✓（read / receive）|
| **set** | 修改 / 写入 | ✗（不可变）| ✓ | ✓（write / send）|
| **drop** | 销毁 / 释放 | ✓ | ✓ | ✓（close / disconnect）|

**注意**：

- **常量**只有 3 个节点：init / get / drop（没有 set，因为不可变）
- **变量**4 个节点齐全：init / get / set / drop
- **IO 资源**4 个节点齐全：open / read / write / close

**示例**：

```rust
// 变量：4 节点
let mut counter = 0;       // init
println!("{}", counter);    // get
counter += 1;               // set
drop(counter);              // drop

// IO 资源：4 节点
let f = File::open("x")?;   // init
let buf = f.read()?;        // get
f.write(&buf)?;             // set
f.close();                  // drop
```

## 4 节点与作用域嵌套

**作用域嵌套时，生命周期的 4 节点要协调**：

```
父作用域生命周期
├─ 子作用域 init
│   ├─ 子作用域状态 init
│   ├─ 子作用域状态 get
│   ├─ 子作用域状态 set
│   └─ 子作用域状态 drop
└─ 子作用域 drop
```

**规则**：

- **子域的 init** 必须在父域的 init 之后、使用之前
- **子域的 get / set** 在子域生命周期内可多次
- **子域的 drop** 必须在父域的 drop 之前
- **所有权的转移**：move 出父域 = 子域变成父域的兄弟，生命周期脱钩

## 所有权规则（呼应域 = owner）

> **域中的状态的所有者就是域本身**——这条规则贯穿所有相关讨论。

- 状态在哪里创建，**所在域**就是其所有者
- 关闭域时，必须关闭其所有状态资源（4 节点中的 drop）
- 状态的所有权可**转移**给其他域（move 语义）—— 转移后原域不再负责销毁
- 状态的所有权可**借用**（borrow）——借用者不拥有，不负责销毁

## 与 4 钩子（init/get/set/destroy）模式的关系

`ts-style` 规则 8「受控的全局状态」有一个** 4 钩子模式**（init / get / set / destroy）——这是本章 4 节点在「受控全局状态」场景下的具体落地：

- `init` — 全局状态初始化一次
- `get` — 任意读
- `set` — 任意写（需受控）
- `destroy` — 程序退出时清理

唯一的 owner 负责 4 钩子的调用时机，其他模块只能 get / set，不能 init / destroy。

- [ ] 程序没有把所有状态塞在全局作用域？
- [ ] 每个作用域都明确：哪些状态属于自己、对外暴露什么接口、生命周期怎么走？
- [ ] 父子作用域的依赖是单向的（父依赖子）？
- [ ] 兄弟作用域之间没有直接通信（必须经过共享父）？
- [ ] 没有循环依赖？
- [ ] 可变全局状态是受控的、4 钩子齐全的（init / get / set / destroy）？
