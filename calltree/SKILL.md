# calltree 速记法

calltree 是一份「程序逻辑的目录」。它**不是**一门编程语言——它故意砍掉所有语法细节，只保留**调用层次**与**控制流**两条信息。

> **目标：用 20 行写清一个 200 行函数在干什么。**

calltree 建立在两个隐含约定之上——这两条不写出来，calltree 就会被当成伪代码或者静态调用图用：

1. **默认不完整** —— calltree 不是源码的镜像，也不追求复刻一个函数里的每一行；它只画对「当前讲述目的」有用的部分，剩下的逻辑靠 `...` 和注释交代。
2. **端到端调用链路** —— 一个程序通常有 N 条独立的端到端调用链（「启动流程」「处理一次 HTTP 请求」「配置热更新」），每条链路单独画一份 calltree，而不是把整个程序塞进一棵大树。一份 calltree 的入口 = 这条链路的「触发点」（不一定是 `main()`）。

读 calltree 的人应该一眼看清三件事：

1. **这条链路从哪里触发、依次调用了谁**（路径前缀直接告诉读者去哪翻源码）。
2. **在什么条件下走哪条分支、循环里做什么**。
3. **最终怎么清理 / 收尾**。

## 一、calltree 的迭代构建

**calltree 不是一次画完的**——它是一份**逐层深入的产物**，从骨架到细节要经过多轮代码探索。试图一步到位地画完整棵 calltree，结果往往是写到一半放弃，或者写出来的不准。

正确的画法是**先框架、后细化、分层迭代**：

### 1. 第一遍：搭骨架（不要展开任何细节）

只画三件事：

1. **入口函数**——一行，零缩进。
2. **一两层调用关系**——每个父节点只列一两个最关键的孩子，**不要**递归展开。
3. **主要控制流节点**——`if` / `loop` / `select!:` 等关键位置用一行注释占位即可。

剩下的全部 `...`。**遇到不懂的细节不要停**——直接 `...`，先让骨架立起来。

```calltree
/* 入口 */
vllm/v1/engine/core.py/run_busy_loop()
    /* 1) 处理输入 */
    core.py/_process_input_queue()
        ...                          // 内部细节待补
    /* 2) 走一步 */
    core.py/_process_engine_step()
        core.py/step_fn()
            vllm/v1/core/sched/scheduler.py/Scheduler.schedule()
            vllm/v1/executor/abstract.py/Executor.execute_model()
            ...                      // sample / update 细节待补
    /* —— 回到 while 顶部 —— */
```

这就是第一遍的产物——只够让人看出「这是个什么循环、有几大步」，但每一大步里都有 `...`。**宁可骨架粗糙，不要细节猜错**——猜错的细节会让读者跟着你错。

### 2. 第二遍及之后：每轮深一层

每次迭代**只选一个子树**往下挖：

- 选当前讲述目的最相关的那个分支。
- 读 1–3 个源码位置（不要读十个）。
- 补上一两个函数签名 + 一句意图注释。
- **不要同时深挖多个子树**——每轮只动一处。

```calltree
/* 第二次迭代后：_process_input_queue 被展开了一格 */
core.py/_process_input_queue()
    loop:                                            // 把队列里所有 pending 都消化掉
        core.py/_handle_client_request()             // 按 request type 分发
            if ADD:
                core.py/EngineCore.add_request()
                    vllm/v1/core/sched/scheduler.py/Scheduler.add_request()
                ...                                  // ABORT / 其他类型待补
```

> 注意节奏：每轮迭代大概只是「补 5–10 行」，不是「补 50 行」。每一格粗细都跟上一步对齐——calltree 的缩进层次反映的是「你知道多少」，不是「代码有多少」。

### 3. 什么时候停

- 每个非 `...` 节点的具体度都够**让读者理解它在做什么**（不需要看源码也能跟上）。
- 总行数到了**讲述目的对应的密度**：说明文档 ~30 行；分析文档 ~50–80 行；超过 ~100 行就该考虑按链路拆（见第二节「端到端调用链路」）。
- **不需要把所有 `...` 都填完**——不重要的细节就让它保持 `...`，那是 calltree 诚实的留白（见第一节「默认不完整」）。

### 4. 反模式

- **想一口气填完** —— 写到一半放弃 / 写出来的不准。calltree 是速记不是规范，**边画边错、错了再改**比「憋一次写对」高效得多。
- **跳过骨架直接画细节** —— 画到一半发现入口选错了、或者发现自己其实想画的是另一条链路，整份作废。
- **每轮同时深挖多个子树** —— 注意力分散，每一处都写得不深。
- **把每行源码都翻译成 calltree** —— 失去压缩比，比直接读源码还累（见第一节「默认不完整」）。
- **一层没稳就想跳到下一层** —— 骨架不稳直接画细节，会写出「细节正确但骨架错」的 calltree，比全错还难救。

## 二、两个隐含约定

### 1. 默认不完整

calltree 是速记，不是规范。一份 calltree 只画对「当前讲述目的」有用的部分：

- 不是每个分支都要写——只写跟当前讲述相关的分支，其它分支用 `else: ...` 或一行注释交代。
- 不是每行代码都要列——只列函数调用、控制流、关键赋值；细节逻辑留在源码。
- 不是每个参数都要写——只写「传了什么、影响什么行为」的关键参数。

判断标准：**如果省略掉这一行，读者无法理解「链路在干什么」或「为什么这么分」，就要写；否则不写。**

`...` 是 calltree 的标志性元素——它主动告诉读者「此处有逻辑，但本次速记不展开」。`...` 不是省略的副产品，是表达「这份 calltree 故意不完整」的明确信号。

> 反模式：试图画一份「把整个函数都写进去」的 calltree。结果就是 calltree 本身变得比源码还难读——你写了 200 行的 calltree 来描述一个 200 行的函数，读者为什么不直接读源码？calltree 的价值在于「压缩比」，不在于「完整」。

### 2. 端到端调用链路

一个程序通常有 N 条相对独立的端到端调用链——每条都从某个「触发点」开始、到某个「终态」结束。calltree 的基本单位不是「整个程序」，而是「一条链路」：

| 程序 | 拆出的 calltree（每份对应一条链路） |
| --- | --- |
| Web 服务 | 启动流程 / 处理一次 HTTP 请求 / 配置热更新 / 优雅关闭 |
| 数据 pipeline | 提交任务 / worker 拉取任务 / 任务失败重试 / 优雅 drain |
| CLI 工具 | 解析命令行参数 / 执行子命令 / 打印帮助 |
| 桌面应用 | 启动 / 用户登录 / 文件保存 / 退出 |

**一份 calltree 的入口 = 这条链路的触发点**，不一定是 `main()`。同一个函数可能出现在多份 calltree 里——例如 `flush_logs()` 既出现在「优雅关闭」链路末尾、也出现在「配置热更新」链路末尾，这是正常的，因为它是两条不同链路的共同步骤。

> 反模式：把整个程序塞进一棵 calltree。后果是树太大、入口不明显、读者要找自己的链路得在几百行里翻。一份 calltree 超过 ~50 行就该考虑按链路拆分。

## 三、语法骨架

```calltree
入口函数()                        // 这条端到端链路的触发点
    准备步骤()
    if 条件:
        分支 A()
            深入一步()
    elif 另一个条件:
        分支 B()
    else:
        默认分支()
    /* 解释这段为什么这么写 */
    ...
    loop:
        每轮做的事()
    清理()                         // 链路的终态
        子清理()
```

## 四、语法元素

### 1. 缩进 = 调用层次

每缩进一级 = 「被父节点调用」。**4 空格**（与 Markdown 嵌套列表兼容，便于直接渲染），不混用 tab。

```
parent()
    child_a()
    child_b()
        grandchild()
    child_c()
```

### 2. 函数名

| 形式 | 含义 | 何时用 |
| --- | --- | --- |
| `func()` | 不带参数的调用 | 默认 |
| `func(args)` | 带参数；参数写法随意（不强调类型） | 想表达传了什么 |
| `load_from_file(char* file)` | 签名风格 | 想强调形参类型（参考源码语言） |
| `func() // 注释` | 行尾注释 | 简短说明 |

calltree 里**没有** `;`、没有 `let`、没有 `var`、没有 `return`、没有可见性修饰符——这些都是「代码层面的细节」，calltree 全部砍掉。

### 3. 文件路径前缀（默认推荐）

calltree 的一项核心价值是「**让读者一眼定位源码**」——读者读到 `init_logger()` 就要能直接打开文件。因此跨文件调用时，**强烈推荐**在函数名前加 `path/to/file.ext/` 前缀；省略路径前缀是反模式。

| 语言 | 常见写法 |
| --- | --- |
| Rust | `src/utils/logger.rs/init_logger()` |
| Go | `pkg/server/server.go/Listen()` |
| TS / JS | `src/api/client.ts/fetch()` |
| Python | `pkg/db/conn.py/open()` |
| C / C++ | `src/net/socket.c/connect()` |

**省略前缀的边界**：仅在「同一份 calltree 反复出现的辅助函数」时可省略——比如所有日志调用都加 `utils/logger.rs/` 太啰嗦，可在 calltree 头部注释里写一句「本 calltree 内未加前缀的函数默认属于 `src/utils/logger.rs/`」。

**省略前缀的场景**：本 calltree 主入口所在文件内的局部 helper（与入口同文件、同模块），可省。

### 4. 控制流关键字

全部以 `:` 结尾，子句缩进一级。calltree 故意**复用多种语言里看起来像的关键字**，挑你目标读者最熟的：

| 关键字 | 含义 |
| --- | --- |
| `if cond:` / `else:` / `elif cond:` | 条件分支 |
| `while cond:` | 条件循环 |
| `for x in xs:` | 遍历循环 |
| `loop:` | 无条件循环 / 主循环（Rust 风格） |
| `match expr:` | 多分支匹配 |
| `select!:` / `select:` | 多路复用（Go / Rust） |
| `try:` / `catch err:` / `finally:` | 异常处理 |
| `switch:` | 多分支（C / JS 风格） |
| `with ctx:` | 上下文管理（Python 风格） |

> **不要纠结用哪个关键字**——同一份逻辑用 `if/else` 还是 `match`，选你**目标读者最熟的语言**那一种。calltree 的目标是「被看懂」，不是「语法正确」。

### 5. 语句与表达式

calltree 不区分「声明」与「语句」——直接写表达式：

```
flavor = quick_flavor()           // 赋值
config.load()                     // 方法调用
result.status == 0                // 裸条件表达式
server_fd                         // 裸标识符（变量 / channel / 资源）
arr.push(item)                    // 带副作用的方法调用
```

> calltree 不强制区分「声明」「赋值」「调用」——三者的边界在源码级有意义，在流程速记里没有意义。

### 6. 注释

```
// 行注释 —— 与一行尾部同写，解释这一句的意图
/* 块注释 —— 单独占一行或多行，解释分支意图 / 设计取舍 */
```

注释是 calltree 的关键组成部分：**省略了语法细节之后，注释是唯一能传达「为什么这么写」的载体。**关键分支、设计取舍、容易踩坑的点——都用注释交代。

### 7. 省略

```
...                               // 一段被刻意跳过的逻辑，读者不需要看
```

`...` 表示「此处有逻辑，但本次速记不展开」。比如「中间省略了 50 行的连接池初始化」——一句话能讲清的事，用 5 行 calltree 写完；展开也讲不清的事，直接 `...`。

`...` 与「默认不完整」是同构的——前者是行级省略，后者是文件级省略。

## 五、完整示例：HTTP 服务启动

来自 `example/server.md`：

```calltree
src/daemon/loop.rs/start_server()
    src/utils/logger.rs/init_logger()
    src/config/load_config()
        load_from_file(char* file)
        src/config/env.rs/load_from_env()
    if arg_quick==0:
        flavor = quick_flavor()   // 使用快处理 flavor
    else:
        flavor = defalut
    /* 初始化数据库连接池子 */
    ...
    loop:
        select!:
            server_fd // server
            worker_fd // worker channel
    loop.rs/clear_resource()
        utils/logger.rs/flush_logs()
```

**怎么读：**

1. 入口是 `start_server()`，在 `src/daemon/loop.rs`——这是一条「启动 → 运行 → 清理」的端到端链路。
2. 先初始化日志、加载配置（配置来源 = 文件 + 环境变量）。
3. 根据命令行参数 `arg_quick` 选 flavor：0 → 快速 flavor，否则默认。
4. 中间省略了「初始化数据库连接池」（细节见源码）。
5. 进入主循环：用 `select!` 多路复用，处理 `server_fd`（服务请求）和 `worker_fd`（worker 通道）。
6. 退出循环后清理资源，最后刷日志。

注意：源文件里 `defalut` 是 typo，这里保留原文——calltree 是速记，不是审查清单，笔误留给 code review 处理。

> 这份 calltree 只画了一条链路。同一个 daemon 还有别的链路——「处理一次请求」「优雅关闭」「配置热更新」——应当各自单独画一份 calltree，而不是都塞进这一棵。

## 六、什么时候用

### ✅ 用

- **讲清楚一段代码在干什么**（聊天 / issue / 邮件 / 评审评论）——尤其跨语言、跨团队时。
- **设计文档 / RFC** 中给出脱离具体语言的执行流程图，让不同语言背景的读者都能秒懂。
- **读陌生代码时** 先在草稿区画 calltree，再决定要不要深读每一行。
- **对比两套实现**：把两份 calltree 并排放，控制流差异一眼可见。
- **复盘 bug 复现路径**：用 calltree 写一遍从入口到触发的链，比写伪代码更紧凑。
- **为一个程序的多个端到端链路分别画 calltree**：一份画「启动流程」、一份画「一次请求的处理」、一份画「优雅关闭」，每份独立、入口清晰。

### ❌ 不用

- 写真正要跑的代码——它是速记，不是编程语言。
- 完整表达算法细节（泛型、类型推导、错误传播链）——这些不在它的目标范围。
- 10 行以内的代码——直接读源码更快，画 calltree 反而绕远路。
- 性能分析 / 数据流分析——calltree 只看**结构**，看不变量、计数、并发原语的具体语义。
- 类型签名 / 接口契约——交给 interface / trait 自己表达，calltree 不抢这份工作。
- 试图把整个程序的所有代码都画到一棵 calltree 里——按端到端链路拆，每份独立。

## 七、约定

1. **缩进**：4 空格（与 Markdown 嵌套列表兼容，便于直接渲染）；tab 不混用。
2. **代码块**：用 ` ```calltree ` 包裹，便于带语法高亮渲染。
3. **混用具体语法是反模式**：在 Rust 代码旁边别写 `Promise<void>`，在 TS 代码旁边别写 `i32`——calltree 的目标就是脱离具体语法，让跨语言读者都能看。
4. **同一份 calltree 只画一个粒度**：要么画到**函数级**（默认，能看到「调用谁」），要么画到**阶段级**（`初始化 → 加载配置 → 进入主循环 → 清理`），别混。
5. **可省略就省略**：类型、可见性、`self` / `this`、错误码、`mod` / `import` / `require`——calltree 里一律不写。
6. **入口置顶零缩进**：一份 calltree 必须有唯一入口，放在第一行、零缩进；其他所有节点都从属于它。入口 = 这条链路的「触发点」，不一定是 `main()`。
7. **跨文件默认加路径前缀**：`path/to/file.ext/func()` 是默认形式；省略仅在「同文件局部 helper」或「calltree 头部声明过默认归属」时可用。
8. **一条链路一份 calltree**：一份 calltree 描述一条端到端链路。同一函数的多个调用点如果在多条不同链路里，会在多份 calltree 中各出现一次。
9. **目标读者决定语言风格**：路径用 `.rs` 还是 `.go`、控制流用 `select!:` 还是 `switch:`——都按目标读者最熟的语言来。
10. **迭代构建，先骨架后细节**：不要试图一次画完。第一遍只搭骨架（一两层调用 + 主要控制流节点），剩下的 `...`；之后每轮只深挖一个子树、补 5–10 行。详见第一节。

## 八、自查

写完一份 calltree，对照这几条：

- [ ] **链路**：这份 calltree 描述的是哪条端到端链路？入口是不是这条链路的「触发点」？
- [ ] **完整度**：有没有画到「不画也行」的部分？多于 ~50 行就该考虑是不是该拆成多份。
- [ ] **入口**：入口函数在第一行、零缩进吗？
- [ ] **缩进**：每个子节点都比父节点多缩进一级吗？
- [ ] **控制流**：控制流关键字都用 `:` 结尾了吗？
- [ ] **路径前缀**：跨文件的函数都加了路径前缀吗？省略的地方有没有在头部声明默认归属？
- [ ] **省略**：想跳过的部分用了 `...` 而不是写「空实现」吗？
- [ ] **注释**：关键分支有没有一句注释解释「为什么这么分」？
- [ ] **语法噪音**：没有任何具体语言的语法噪音（`let` / `fn` / `i32` / `Promise<>` / `;`）吗？
- [ ] **可读性**：一个不熟悉这份代码的读者，能在 1 分钟内画出 back-of-envelope 的调用图吗？
- [ ] **可定位**：读者看到任一函数，能不能在 30 秒内打开对应源文件？
