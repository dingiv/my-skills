# 新项目 Bootstrap 流程

> **目的**：当 agent 面对「做一个新项目」「从零设计一个 X」「帮我搭一个 Y 系统」这类请求时，按明确步骤引导，**不会上来就开始写代码**。

**适用触发**（出现以下任意一条即应启动本流程）：

- 用户说「我想做一个 XX 系统」
- 用户说「帮我设计一个 XX」
- 用户说「从零开始一个 XX 项目」
- 任何**没有现存代码、需求模糊**的新建项目请求

**关键约束**：**不要跳过任何一步**。每一步完成后必须向用户确认，才能进入下一步。如果用户主动跳步，礼貌地把当前步骤补完，再继续。

---

## 第 1 步：需求阐述（跟用户对话）

**目标**：把模糊的「想做一个项目」逼成清晰的需求边界。这一步只产生对话，不产出文件。

**核心问题骨架**（必须问到这几类，缺一不可）：

1. **项目目的** —— 要解决什么问题？为什么做？替代什么 / 补足什么空缺？
2. **目标用户** —— 谁会用？典型使用场景是什么？
3. **核心场景** —— 最关键的 1–3 个场景是什么？每个场景的「触发 + 输入 + 终止」是什么？
4. **完成标准** —— 做到什么程度算「做完了」？有没有可验证的判定标准？
5. **约束条件** —— 技术栈、性能、部署、时间、团队规模、必须用 / 不能用的东西？

**自由追问**（agent 应根据回答自行判断，决定问什么 / 问几个）：

- 用户的回答哪里不清晰 → 追问
- 用户的回答前后矛盾 → 标注冲突让用户澄清
- 用户跳过了关键问题 → 礼貌地补问
- 用户已经覆盖了所有骨架 → 不必硬凑问题

**第 1 步结束标准**（满足以下全部）：

- 上述 5 类问题都得到了至少粗略的回答
- agent 能向用户复述「所以你的项目是 X，主要做 Y，服务 Z，对吗？」
- 用户确认无误

**不要做**：

- 不要替用户回答（「你是不是想要 X？」——这会把需求引导向 agent 的预设）
- 不要直接跳到设计（「我猜你想要的是 Y，对吗」——这是把设计阶段的事提前做）
- 不要一次问超过 5 个核心问题（用户会疲劳，分多轮比一次性塞一堆好）
- 不要在这一步写任何代码 / 文档 / 文件

---

## 第 2 步：生成需求文档

**输入**：第 1 步的对话结论。

**输出**：一份结构化需求文档，存为项目内的 `REQUIREMENTS.md`（或 `docs/requirements.md`，与项目习惯对齐）。

**文档模板**：

```markdown
# [项目名] 需求文档

## 项目目的
[1–2 段，从第 1 步整理]

## 目标用户
- [用户类型 1]：[典型场景]
- [用户类型 2]：[典型场景]
- ...

## 核心场景
### 场景 1：[名字]
- 触发：[什么会启动这个场景]
- 输入：[外部带来什么]
- 输出：[产出什么]
- 终止：[什么时候算结束]

### 场景 2：[名字]
[同上]

## 完成标准
- [ ] 标准 1（可验证）
- [ ] 标准 2（可验证）
- ...

## 约束条件
- 技术栈：
- 性能：
- 部署：
- 时间：
- 其他：

## 范围外（明确不做的事）
- [从对话中识别，标注哪些是用户明确说不做的]
```

**第 2 步结束标准**：

- 文档已写入文件
- agent 把文档内容向用户复述
- 用户确认无误（特别是「范围外」一节要明确，避免遗漏）

**不要做**：

- 不要在这一步设计架构（那是第 3 步的事）
- 不要在这一步设计接口（那是第 4 步的事）
- 不要在这一步写代码

---

## 第 3 步：设计端到端调用链路

**输入**：第 2 步的需求文档。

**输出**：N 条端到端链路的 calltree 草图（每条核心场景 = 1 条链路）。

**操作**：

1. 从需求文档的「核心场景」出发，每条核心场景 = 1 条链路
2. 每条链路用 `calltree` 语法表达（参考 `calltree` skill）
3. **不要求完整**——重点是「主链路」，分支细节用 `...` 留白，传递骨架而非细节
4. 链路要标清楚触发点、终止条件、关键步骤

**链路图骨架示例**：

```calltree
触发点()                              // 这条链路的触发
    step1()
    step2()
    if 条件:
        分支A()
    else:
        分支B()
    ...                              // 细节留白
    终止()                            // 这条链路的终止
```

**第 3 步结束标准**：

- 每个核心场景都有对应的 calltree
- calltree 的触发点 / 终止条件 / 主要步骤可读
- 用户对 calltree 整体走向没有异议（细节留白可接受）

**不要做**：

- 不要在这一步定义接口
- 不要在这一步设计模块结构
- 不要在这一步考虑实现
- 不要画超过 N 条链路（N = 核心场景数）——非核心链路留到模式二再补

---

## 第 4 步：设计对外接口

**输入**：第 3 步的链路图。

**输出**：对外接口契约（伪代码）。

**操作**：

1. 从每条链路中识别关键接口节点：
   - **输入接口**——链路从哪里接收外部输入
   - **关键产出接口**——链路在哪里产出关键结果
   - **终止接口**——链路在哪里收尾 / 通知外部
2. 每个接口用伪代码定义（**不实现**），写出：
   - 输入 / 输出类型
   - 失败语义（哪些错误会抛 / 返回什么）
   - 生命周期契约（`init` / `destroy` / `connect` / `close`）
3. 接口应当由「链路需求」驱动，不是反过来——先有链路再有接口

**接口伪代码骨架示例**：

```typescript
// [接口名 + 一句话用途]
interface SomeInterface {
  // 输入
  doX(input: InputType): OutputType

  // 失败语义
  //   - InvalidInput → InvalidInputError
  //   - IO 失败 → IOError

  // 生命周期
  init(): void                  // 副作用（连接 / 订阅）在此启动
  destroy(): void               // 关闭后不可再调用
}
```

**第 4 步结束标准**：

- 每条链路上关键接口都有定义
- 接口伪代码自洽（不引用未定义的东西）
- 用户对接口「外观」满意（外观 = 调用方看接口的方式）

**不要做**：

- 不要在这一步写实现
- 不要在这一步决定数据结构
- 不要在这一步拆分模块
- 不要在这一步写单元测试

---

## 流程结束

完成第 4 步后，bootstrap 流程结束。产出物清单：

- ✅ 需求文档（`REQUIREMENTS.md`）
- ✅ N 条端到端 calltree（可放 `docs/calltrees/` 或留在对话里）
- ✅ 对外接口契约伪代码（可放 `docs/interfaces/` 或留在对话里）

**后续可以**：

- 进入模式一「架构新项目」（见 [modes.md](modes.md)）继续走完第 2.3 / 2.4 步（依赖时序 + 空间优化）
- 进入 `rust-style` / `ts-style` 开始编码
- 进入迭代开发（边实现边回头修订架构）

---

## 常见偏离与纠正

| 偏离 | 表现 | 纠正 |
| --- | --- | --- |
| **跳过第 1 步** | 用户给出简短描述后，agent 立刻开始设计接口 | 礼貌地回到第 1 步：「我想先跟你确认几个关键问题，确保后面不偏」 |
| **第 1 步问太细** | agent 把用户问到烦，问题清单 20+ 条 | 收敛到骨架 5 类；非核心问题放到后续迭代 |
| **第 2 步替用户决定范围外** | agent 自己填了「不做 X」但用户没说 | 明确标注「待确认」让用户决定 |
| **第 3 步变成完整设计** | calltree 画得太细，陷入实现细节 | 用 `...` 留白；只在用户追问时展开 |
| **第 4 步提前开始实现** | 接口伪代码变成了完整函数 | 立即停手，回到伪代码级别 |
