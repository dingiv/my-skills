# 域的组合（Composition）

> **程序 = 一个最大的域；域里有域；每个域都有自己的状态机；子状态机组合成大状态机。** 组合的规则就是约束——用约束把噪声「雕刻」成最终形态。

## 一句话

> **域 = 自相似的递归结构；程序 = 被约束雕刻出来的状态机。**

## 域的泛化（域里有域）

- **程序本身是一个域**——最大的全局域
- **域里有域**——每个域可以包含若干子域
- **每个子域和父域之间是相似的结构**——这就是**自相似性 / 递归性**

具体到不同语言：

```
程序（最大的全局域）
  └─ 文件（package / module）
      └─ 类（class / struct / trait）
          └─ 函数（function / method）
              └─ 块（block / closure）
```

每一层都满足相同的形态：

| 项 | 内容 |
| --- | --- |
| 状态 | 变量（全局 / 成员 / 局部） |
| 行为 | 方法 / 函数 / 块 |
| 生命周期 | init / destroy |
| 接口 | public / exported |

**关键观察**：每一层都是**完整的状态机**——有自己的初始状态、转移函数、终态。子状态机之间通过接口通信。

## 状态机组合

程序 = 多个子状态机的**组合**。

问题：应该以怎样的方式组合它们？

答案：**用约束雕刻**。

### 扩散模型类比

扩散模型（生成图片的深度学习模型）的工作方式：

1. **起始**：纯噪声（无序状态）
2. **加约束**：逐步加入约束（"这里要有树"、"那里要有河"、"天空是蓝色"）
3. **最终**：满足所有约束的图片——一个**确定**的形态

**程序设计同理**：

1. **起始**：空白（无任何代码）
2. **加约束**：逐步加入约束
   - "程序要监听 HTTP 请求"（事件源约束）
   - "GET /api/users 要返回用户列表"（接口约束）
   - "用户列表要从数据库读"（依赖约束）
   - "数据库连接要在 handler 之前建立"（时序约束）
3. **最终**：满足所有约束的程序

**每加一个约束，搜索空间变小**。约束越多 → 状态空间越收缩 → 最终形态越确定。

> 这就是为什么「架构设计」是可能的——不是因为我们有完美的设计方法，而是因为约束足够多时，符合约束的程序形态是**有限**的、甚至**唯一**的。

## 组合的约束

约束是程序形态的「雕刻刀」。最直接、最重要的约束是**依赖约束**——时序上的约束。

### 依赖约束（第一个，最重要）

> **一个域要使用另一个域的资源时，必须在使用动作发生之前把资源准备好。**

这就是 [timing.md](timing.md) 第 1 条「依赖前向包含」：

```
A 依赖 B → B 的生命周期必须前向包含 A 使用 B 的时间窗
```

具体形式：

| 依赖类型 | 准备时机 | 使用时机 |
| --- | --- | --- |
| 变量依赖 | 赋值语句 | 读取语句 |
| 资源依赖 | `open` / `connect` | `read` / `write` |
| 状态依赖 | `init` | handler 调用 |
| 接口依赖 | 接口定义 | 接口调用 |

### 其他约束（按重要性排序）

依赖约束只是第一把刀。其他约束：

1. **依赖约束**（时序）——已在 [timing.md](timing.md) 详述
2. **逻辑约束**（需求）——需求明文指定的规则（"先 A 再 B"、"B 失败回滚 A"）
3. **工程约束**（项目）——命名、路径、依赖可见性

每一把刀都在收缩搜索空间。**约束越多，程序形态越收敛**。
