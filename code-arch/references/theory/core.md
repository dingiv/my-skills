# 核心论断：程序即状态机

**论断**：所谓程序的功能，就是在它的生命周期存在期间，按照给定的路径感知外界输入，并做出预期的输出。简单来说，就是一个**状态机编排**。

这一论断有三层意义——它们共同决定了后续所有架构动作的方向。

**1. 任何程序都能被画成一张状态图。** 从初始状态出发，沿着状态转移函数运行，直到终止状态。CLI、库、服务、嵌入式，无一例外。区别只在于状态数与转移函数的复杂度。把任何一段代码先当成状态机去看，是拆解陌生项目最便宜的入口。

**2. 复杂度封装效应。** 实现需求的复杂度被状态机封装——不是被消灭，而是被装进有边界的空间里。调用方看到的是契约（状态 + 行为），不必关心内部如何编排。封装的不变式由 `rust-style` 的「实现 struct 不公开」、`ts-style` 的「实现 class 不 export」保证：复杂度不会泄漏到调用侧。

**3. 状态机的复杂度 = 空间 × 时序。**

- **空间复杂度** = 状态数 + 转移函数数。模块化、类型系统、单一职责都在压缩它。
- **时序复杂度** = 单路径长度 × 多路径调度。生命周期、并发、依赖方向都在约束它。

需求越多 → 空间复杂度变复杂；需求越复杂（多入口、多分支、并发、生命周期交叉）→ 时序复杂度变复杂。**架构设计的本质**：把指数增长的状态空间，通过合理的空间封装（模块 / 接口 / 类型 / 生命周期），压回到线性可管理的范围。

> 程序内任何问题的最终归属，都是这台状态机里某个状态或某条转移。找不到状态归属的需求，要么不是真需求（应剔除），要么是需求没拆到位（应继续拆）。
